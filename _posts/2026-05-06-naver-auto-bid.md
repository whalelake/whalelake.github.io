`naver-auto-bid`는 네이버 검색광고 키워드의 입찰가를 자동으로 분석하고 조정하는 시스템이다. 겉으로 보면 “성과가 좋으면 올리고, 나쁘면 내리는” 간단한 자동화처럼 보일 수 있다. 하지만 실제로 만들다 보면 입찰 자동화의 핵심은 가격 변경 로직이 아니라, 변경해도 되는 상황과 멈춰야 하는 상황을 구분하는 운영 체계라는 걸 금방 알게 된다.

검색광고의 입찰가는 매출, 클릭, 전환, 노출 순위, 예산 소진 속도, 이상 클릭 가능성 같은 여러 신호가 한꺼번에 섞인 값이다. 그래서 자동화는 단순한 규칙 몇 줄로 끝나지 않는다. 데이터가 충분한지, 최근 성과가 우연인지, 현재 전략이 효율 중심인지 순위 확보 중심인지, 조정 폭이 과도하지 않은지까지 함께 판단해야 한다. 이 프로젝트는 그 판단 과정을 수집, 분석, 실행, 모니터링 흐름으로 나눠 구현한 실험이었다.

## 자동 입찰은 의사결정 파이프라인이다

이 프로젝트의 구조는 꽤 명확하다. 먼저 네이버 검색광고 API에서 캠페인, 광고그룹, 키워드, 성과 데이터를 수집한다. 다음으로 키워드별 지표를 분석해 조정 후보를 만들고, 전략별 규칙에 따라 입찰가 변경안을 계산한다. 마지막으로 변경 가능 여부를 점검한 뒤 실제 API 호출을 실행하고, 모든 결과를 데이터베이스와 로그에 남긴다.

흐름으로 보면 `DataCollector -> BidAnalyzer -> BidExecutor -> Monitoring`에 가깝다. `main.py`는 이 흐름을 실행 모드로 묶는다. 최초 테이블을 준비하는 `setup`, 웹 대시보드를 띄우는 `dashboard`, 자동 입찰 루프를 실행하는 `auto`, 한 번만 분석과 조정을 돌려보는 `single` 모드가 있다. 운영 중에는 대시보드를 통해 추천 조정, 실행 결과, API 호출, 최적화 사이클을 확인할 수 있게 했다.

이렇게 나눈 이유는 자동화가 한 덩어리로 붙어 있으면 위험하기 때문이다. 수집 오류인지, 분석 오류인지, 실행 오류인지 구분할 수 없으면 자동화는 곧 블랙박스가 된다. 광고비가 걸린 시스템에서 블랙박스는 속도가 아니라 리스크다. 그래서 각 단계가 독립적으로 기록되고, 문제가 생겼을 때 어느 단계에서 판단이 틀어졌는지 추적할 수 있어야 했다.

## 전략은 하나가 아니라 여러 개여야 한다

입찰 최적화에서 “좋은 입찰가”는 하나로 정의되지 않는다. 어떤 계정은 효율을 최우선으로 봐야 하고, 어떤 캠페인은 신규 고객 확보를 위해 더 공격적인 노출이 필요하다. 또 어떤 키워드는 목표 순위를 지키는 것이 중요하고, 어떤 키워드는 CPA나 ROAS 기준으로 보수적으로 움직여야 한다.

그래서 프로젝트에는 여러 입찰 전략을 넣었다. `EFFICIENCY`는 성과 효율을 중심으로 움직이고, `AGGRESSIVE`는 성장과 노출 확대에 무게를 둔다. `CONSERVATIVE`는 조정 폭을 줄여 안정성을 우선하고, `BALANCED`는 효율과 성장 사이의 균형점을 찾는다. `POSITION`은 목표 순위 유지에 집중한다.

이 구분이 중요한 이유는 자동화의 목적을 코드 안에 명시하기 때문이다. 전략이 없으면 모든 키워드가 같은 기준으로 평가된다. 하지만 실제 광고 운영은 그렇게 단순하지 않다. 브랜드 키워드, 전환 키워드, 탐색 키워드, 테스트 키워드는 서로 다른 역할을 가진다. 자동화 시스템도 그 차이를 인정해야 한다.

## 안전장치가 본체에 가깝다

자동 입찰 시스템에서 가장 먼저 떠올리는 기능은 “얼마를 올릴 것인가”일 수 있다. 하지만 실제로 더 중요한 질문은 “어디까지 올릴 수 있는가”와 “언제 멈출 것인가”다. `naver-auto-bid`에는 이 질문에 답하기 위한 여러 안전장치를 넣었다.

입찰가는 최소 70원, 최대 100,000원 범위 안에서만 움직이도록 제한했다. 단일 조정 폭이 ±50%를 넘지 않도록 막고, 하루 동안 실행 가능한 변경 건수에도 한도를 뒀다. 실제 입찰가를 바꾸기 전에 드라이런으로 추천안만 확인할 수 있고, 문제가 생겼을 때 최근 변경을 되돌리는 롤백 흐름도 준비했다.

이런 장치는 화려하지 않지만 자동화의 신뢰를 만든다. 광고 운영자는 자동화가 똑똑하다는 말보다, 사고가 났을 때 어디서 멈추고 어떻게 되돌릴 수 있는지를 더 중요하게 본다. 특히 입찰가는 계정 전체 비용에 직접 영향을 준다. 그래서 자동화는 가속 페달보다 브레이크를 먼저 설계해야 한다.

## 이상 클릭 탐지는 성과 데이터의 품질 문제다

이 프로젝트에서 흥미로웠던 부분 중 하나는 클릭 부정 탐지였다. 이상 클릭은 단순히 보안이나 부정 사용자의 문제가 아니다. 입찰 최적화 관점에서는 성과 데이터의 품질을 흐리는 문제다. 클릭이 많아 보이지만 전환으로 이어지지 않는 키워드가 있다면, 그 원인이 광고 소재나 랜딩페이지일 수도 있고, 비정상 클릭 패턴일 수도 있다.

자동 입찰 시스템이 이런 차이를 무시하면 잘못된 결론을 낸다. 클릭 수만 보고 관심이 높다고 판단하거나, 전환이 없다는 이유로 좋은 키워드를 성급하게 낮출 수 있다. 그래서 이상 클릭 패턴을 별도로 탐지하고, 입찰 판단의 보조 신호로 다루는 구조가 필요했다.

이 지점에서 자동화는 다시 데이터 분석 문제로 돌아온다. 성과 지표는 있는 그대로의 진실이 아니라, 해석해야 하는 관측값이다. 자동 입찰은 관측값 위에서 움직이기 때문에, 데이터가 어떤 조건에서 왜곡될 수 있는지 함께 추적해야 한다.

## 대시보드는 장식이 아니라 운영 장치다

자동화 프로젝트에서 대시보드는 종종 나중에 붙이는 화면처럼 취급된다. 하지만 입찰 시스템에서는 대시보드가 핵심 운영 장치에 가깝다. 사람이 현재 상태를 볼 수 없으면 자동화는 신뢰를 얻기 어렵다.

`naver-auto-bid`의 웹 대시보드는 Flask 기반으로 구성했다. 실시간 통계, 키워드 성과, 추천 조정안, 실행 이력, API 호출 로그, 모니터링 상태를 확인할 수 있도록 했다. 화면 기술 자체는 복잡하지 않다. 중요한 것은 “자동화가 지금 무엇을 판단했고, 무엇을 바꿨으며, 왜 그렇게 했는가”를 사람이 따라갈 수 있게 만드는 것이다.

특히 입찰 변경 이력과 API 호출 로그는 단순한 기록을 넘어 감사 추적의 역할을 한다. 어느 시점에 어떤 키워드가 어떤 전략으로 조정됐는지 남아 있어야 나중에 성과를 해석할 수 있다. 자동화의 결과만 보면 운이 좋았는지 판단이 맞았는지 알기 어렵다. 과정이 남아야 개선할 수 있다.

## 운영 자동화는 기억을 가져야 한다

이 프로젝트를 만들며 가장 크게 남은 감각은, 운영 자동화에는 기억이 필요하다는 것이다. 한 번의 API 호출, 한 번의 입찰 변경, 한 번의 분석 결과가 서로 끊어져 있으면 시스템은 매번 처음 판단하는 셈이 된다. 하지만 실제 운영은 누적된 맥락 위에서 이루어진다.

그래서 데이터베이스에는 API 호출 로그, 입찰 변경 이력, 최적화 사이클, 모니터링 결과, 키워드 성과 캐시를 나눠 저장하도록 했다. 이 구조가 있어야 “이번 조정이 지난번보다 나아졌는가”, “특정 전략이 어떤 캠페인에서 잘 먹히는가”, “최근 성과 변화가 입찰 조정 때문인가” 같은 질문을 할 수 있다.

자동화가 기억을 갖는 순간, 단순 반복 작업은 실험 시스템으로 바뀐다. 실행하고, 기록하고, 비교하고, 다시 조정하는 루프가 생긴다. 광고 운영에서 중요한 것도 결국 이 루프다. 정답 입찰가를 한 번 찾는 것이 아니라, 시장과 계정 상태가 바뀔 때마다 더 나은 판단으로 이동하는 것이다.

## 다음에 더 다듬고 싶은 것

다음 단계로는 백테스팅을 강화하고 싶다. 실제 입찰가를 바꾸기 전에 과거 데이터 기준으로 전략별 결과를 비교할 수 있다면, 운영자가 더 안심하고 자동화를 켤 수 있다. 단순 드라이런이 “이번 추천안”을 보여준다면, 백테스팅은 “이 전략이 과거에 어떤 성향을 보였는가”를 보여준다.

전략 비교 화면도 더 발전시킬 수 있다. 같은 키워드에 대해 `EFFICIENCY`, `BALANCED`, `POSITION` 전략이 각각 어떤 입찰가를 추천하는지 나란히 보여주면, 운영자는 전략의 차이를 더 직관적으로 이해할 수 있다. 여기에 예산 소진 속도와 캠페인 목표를 함께 반영하면 더 현실적인 의사결정 도구가 된다.

마지막으로, 자동화 권한을 캠페인 단위로 더 세밀하게 나누고 싶다. 모든 캠페인을 한 번에 자동화하는 것보다, 테스트 캠페인에서 먼저 적용하고 성과가 확인되면 확장하는 방식이 안전하다. 자동화는 크게 켜는 기능이 아니라, 작게 믿음을 쌓아가는 기능이어야 한다.

`naver-auto-bid`를 만들며 배운 것은 입찰 자동화의 본질이 “자동으로 바꾸는 것”이 아니라는 점이다. 중요한 것은 데이터를 읽고, 전략을 선택하고, 안전하게 실행하고, 결과를 기억하는 구조다. 좋은 자동화는 사람을 배제하지 않는다. 사람이 더 적은 피로로 더 나은 판단을 할 수 있게 돕는다.
